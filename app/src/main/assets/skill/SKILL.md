# 사용 패턴 → 루틴 제안

숫자를 문장으로 옮기는 일이 아니다. **반복 패턴 중 사용자 자신도 인지 못 하는
것을 찾아, 맥락상 말이 되는 것만 실행 가능한 제안으로 바꾸는** 일이다.

두 가지 실패를 모두 경계한다:
- 통계만 보고 제안 — 횟수 1등이어도 서사가 없으면 우연이거나 병행일 뿐이다.
- 서사만 보고 제안 — 그럴듯한 이야기는 언제나 지어낼 수 있다. 통계가 먼저 문을 열어야 한다.

## 절대 규칙

1. **관측 창을 먼저 확인한다.** `meta.fullDays` 기준. 지표마다 커버리지가 다르면
   (알림 리스너 시작일 등) 그 사실을 confidence 에 반영한다.
2. **품질을 먼저 읽는다.** `quality.warnings` 와 검산은 앱이 이미 해뒀다.
   `references/artifacts.md` 로 무엇이 처리됐고 무엇을 여전히 의심할지 확인한다.
3. **서사가 써지지 않으면 제안하지 않는다.** 후보마다 "사용자가 왜 이렇게 하는가"를
   한 문장으로 써야 하고, 그 문장이 통계의 세부와 맞물려야 한다.
4. **개수를 채우지 않는다.** 확실한 게 2개면 2개만 낸다. 남발된 제안은 팝업 신뢰를
   깎고, 수락률이라는 ground truth 를 오염시킨다.
5. **존재하는 자동화만 제안한다.** 트리거·액션은 `references/proposal-rules.md` 의
   허용 목록에 있는 것만. 없는 기능을 지어내지 않는다.
6. **기기≠사람.** 통신·네트워크·연결은 기기의 상태다. 사람의 위치·행동은 유추이고,
   유추라는 사실을 narrative 와 confidence 에 끌고 간다.
7. **사용자의 인격·건강·의지를 평가하지 않는다.** 패턴을 바꾸라는 제안이 아니라
   패턴을 편하게 만드는 제안을 한다.

## 절차

### 1단계 — 데이터 지형도

`meta` 와 `diagnostics` 로 관측 창·커버리지를 표로 정리한다. 지표별 관측 창이
다르면(알림 리스너, BT 등) 이후 confidence 판정의 상한이 된다.

### 2단계 — 품질 확인

`references/artifacts.md`. 앱이 처리한 것은 검산 필드로 확인만 하고,
여전히 남는 함정(재갱신, 백그라운드, 타인 사용 구간)을 체크한다.
`quality.reconciliationDelta < 0` 이면 앱 지표 기반 제안을 전부 보류한다.

### 3단계 — 후보 발굴 (통계가 문을 연다)

`references/proposal-rules.md` 의 카테고리별 통계 문턱으로 후보를 모은다.
여기서는 거르지 않는다 — 문턱을 넘은 모든 후보를 다음 단계로 보낸다.
유명한 조합만 보지 말 것: 문턱은 기계적으로 적용해야 사용자가 인지 못 하는
패턴이 걸려 나온다.

### 4단계 — 맥락 판정 (서사가 문을 통과시킨다) ★핵심

후보마다 세 질문에 답한다.

1. **목적성** — 이 앱/트리거는 무엇을 위한 것인가. 당신의 세계지식을 쓴다.
   (증권 앱은 거래·시세, 금융 슈퍼앱은 결제+커뮤니티, 이어버즈는 듣기의 시작)
   세계지식이 안 닿는 앱은 apps.category(개발자 선언 분류, 없을 수 있음)와
   사용 형태(secondsPerLaunch 짧으면 확인형, 길면 몰입형)로 목적을 추론하고,
   그래도 목적이 안 서면 그 앱에 대한 제안은 내지 않는다.
2. **행동 서사** — 이 통계를 만드는 사용자 행동을 **한 문장으로** 쓴다.
   "커뮤니티 반응 확인 ↔ 거래·시세 확인의 반복" 처럼 목적이 이어져야 한다.
3. **서사 검증** — 그 서사가 통계의 세부와 맞는가.
   - 간격: 이어지는 행동이라기엔 길지 않은가 (수십 초 이상이면 의심)
   - 홈 경유율: 한 흐름이면 낮고, 별개 작업의 병행이면 높다
   - 방향비: 왕복인가 한 방향 흐름인가 — 서사와 맞아야 한다
   - 시간대·상태: appContext 가 서사를 지지하는가
   - **같은 트리거에 여러 앱이 걸리면 연쇄 횟수가 아니라 appContext 의
     조건부 비율 기울기로 하나를 특정한다.** 횟수는 그 앱의 전체 사용
     빈도에 오염된다 — 하루 30번 여는 앱은 아무 트리거 뒤에나 자주
     나타난다. 트리거에 묶인 앱은 "그 상태에서 실행되는 비율"이 다른
     앱들보다 뚜렷이 높은 쪽이다 (횟수가 적어도).

서사가 서지 않거나 대안 서사(우연, 병행, 자동 동작)가 더 그럴듯하면 그 후보는
`rejected` 로 보내고 사유를 서사로 쓴다. **횟수 1등이 기각되고 횟수 적은 후보가
통과하는 일은 정상이다** — 이 단계가 하는 일이 바로 그것이다.

### 5단계 — 교차 검증

`references/cross-analysis.md`. 통과한 서사를 다른 지표가 지지하는지 본다.
분할화면 실측이 "동시 확인" 서사를, 조건부 비율의 기울기(연결 중 실행 %)가
"의식(ritual)" 서사를 지지하는 식이다. 지지 지표는 evidence 에 추가한다.
페르소나(하루 리듬·요일·수면)는 서사의 가중치다 — 근거로 쓰되 전제로 쓰지 않는다.

### 6단계 — 제안 생성

`references/proposal-rules.md` 의 JSON 스키마로만 출력한다.
개수 정책: 전체 최대 5, 카테고리당 최대 2, confidence → 반복일수 순.
탈락 후보 중 알려줄 값어치가 있는 것은 `rejected` 에 사유와 함께.
`analysisNote` 에 관측 창·품질 경고·전반 요약을 담는다.

## 참조 파일

| 파일 | 언제 |
|---|---|
| `references/artifacts.md` | 2단계. 앱이 처리한 것 / 여전히 의심할 것 |
| `references/metrics.md` | 3단계. 리포트 필드 사전과 독법 |
| `references/proposal-rules.md` | 3·6단계. 카테고리 문턱, 스키마, 허용 목록 |
| `references/cross-analysis.md` | 5단계. 서사를 지지/반박하는 지표 조합 |
| `references/worked-example.md` | 절차가 실제로 어떻게 갈리는지 세 사례 |

## 마무리 체크리스트

- [ ] 모든 제안에 narrative 가 있고, 통계 세부와 모순되지 않는가
- [ ] 트리거·액션이 전부 허용 목록에 있는가
- [ ] 개수를 채우지 않았는가 (약한 후보를 승격시키지 않았는가)
- [ ] 관측 창이 짧은 지표(BT 등)로 만든 제안의 confidence 를 낮췄는가
- [ ] rejected 에 "통계는 강하나 서사가 약한" 후보를 남겼는가
- [ ] 파생 추정(수면·장소·이동)을 사실처럼 쓰지 않았는가
