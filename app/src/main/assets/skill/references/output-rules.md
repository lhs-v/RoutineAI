# 서술 규칙 · 자동화 제안 · 금지 사항

---

## 1. 발견을 쓰는 형식

발견 하나는 네 부분으로 이루어진다. 순서를 지킨다.

```
① 주장     — 한 문장. 숫자가 아니라 의미로 시작한다.
② 근거     — 어떤 수치가 그 주장을 만드는가. 관측 창과 표본 수 포함.
③ 판정 근거 — 왜 이게 우연이나 아티팩트가 아닌가.
④ 한계     — 무엇을 모르는가.
```

**②를 ①보다 먼저 쓰면 독자는 무슨 말인지 모른 채 숫자를 읽는다.** 주장이 먼저다.

### 좋은 예

> **기상은 알람이, 취침은 아무것도 통제하지 않습니다**
> 9일 밤 중 6일이 거의 같은 시각에 기상(편차 ±1.1시간)인데 취침은 3시간 20분 범위로 흩어져 있습니다. 그 결과 수면 중앙값이 5.8시간, 가장 짧은 밤은 3.4시간이었습니다.
> 근거: 화면 활동 3시간 이상 공백 9건. 기상 시각의 집중도가 취침보다 뚜렷하게 높습니다.
> 한계: 화면을 안 봤다는 것이지 잤다는 증거는 아닙니다.

### 나쁜 예

> 하루 평균 수면이 6.8시간으로 규칙적입니다.

무엇이 문제인가 — 평균만 썼고(C2 위반), 관측 창과 표본을 안 밝혔고, "규칙적"이라는 판정의 근거가 없고, 파생 추정임을 숨겼다. 실제로 이 문장은 **가장 긴 밤 하나를 전체로 착각한 결과**였다.

## 2. 등급별 어휘

| 등급 | 써도 되는 표현 | 쓰면 안 되는 표현 |
|---|---|---|
| 확인됨 | "~합니다", "~입니다" | — |
| 유력 | "~로 보입니다", "~에 가깝습니다" | "~합니다" |
| 가설 | "~일 가능성이 있습니다", "~라면 설명이 됩니다" | "~로 보입니다" 이상 |

**등급을 올리고 싶으면 데이터를 더 가져와야지 어휘를 바꾸면 안 된다.**

---

## 3. 숫자를 쓰는 방식

- **비율에는 분모를 붙인다.** "54%"보다 "729번 중 391번(54%)".
- **긴 숫자는 의미 단위로 환산한다.** "26,665회"만 쓰지 말고 "하루 88회꼴"을 함께.
- **평균을 쓸 때는 반드시 중앙값이나 범위를 같이 쓴다.**
- **파생 지표는 계산 방식을 한 번은 밝힌다.** "폰을 놓은 시각부터 다시 켠 시각까지".
- **관측 창을 문장 안에 넣는다.** "9일 중 7일", "102일치".

---

## 4. 기각한 후보를 밝히기

검토했다가 버린 해석 중 **독자가 알면 유용한 것**은 남긴다. 이건 분량 낭비가 아니라 신뢰의 근거다.

특히 이런 것들:

- 아티팩트로 밝혀진 것 — "A 앱이 하루 117분으로 잡혔지만 화면 꺼진 시간이 누적된 것이었고, 실제로는 1.8분입니다."
- 표본 부족으로 못 쓴 것 — "주말 표본이 2일뿐이라 주말 패턴은 관찰로만 둡니다."
- 대안 가설을 못 죽인 것 — "두 지표가 함께 움직이지만 세 번째 지표가 없어 원인을 특정할 수 없습니다."

## 5. 자동화 제안 도출

발견을 제안으로 바꿀 때는 세 조건을 전부 확인한다. 하나라도 빠지면 제안하지 않는다.

**① 반복성** — 관측 창의 절반 이상에서 나타나는가. 일회성 패턴은 자동화 대상이 아니다.

**② 트리거 가능성** — 기기가 감지할 수 있는 조건에 걸리는가.
감지 가능: 시각, 요일, 네트워크 연결/해제, 기기 연결(이어폰·차량), 알람 해제, 앱 실행, 배터리 상태, 위치.
감지 불가능: 기분, 업무 시작, 대화 중, 피곤함.

**③ 비용 대비 효과** — 설정 한 번으로 반복 비용이 사라지는가. 매번 사용자의 판단이 필요하면 자동화가 아니다.

### 제안의 우선순위

```
1순위  이미 하고 있는 걸 더 쉽게      (동시 사용 조합 → 앱 페어)
2순위  통제 없는 쪽에 통제 장치를      (유형 3의 흔들리는 쪽)
3순위  소음 줄이기                   (응답 불필요 알림 정리)
4순위  마찰 없애기                   (홈 경유 많은 전환 쌍)
5순위  총량 줄이기                   (가장 어렵고 실패율 높음)
```

**5순위를 1순위로 제안하지 않는다.** "적게 쓰세요"는 데이터가 없어도 할 수 있는 말이고, 성공률이 가장 낮다.

### 제안 형식

각 제안은 **왜 이게 되는지를 데이터로 설명**하고, **구체적인 설정 경로**를 준다. 경로를 못 쓰면 그 제안은 아직 완성이 아니다.

```
제목    — 무엇을 할지
근거    — 어떤 발견에서 나왔는지, 수치와 함께
방법    — 실제 설정 경로 또는 동작
효과    — 가능하면 정량적으로 ("하루 394건 → 약 235건")
```

## 6. 금지 사항

### 하지 않는다

- **장소·인물·활동의 정체를 추정하기.** Wi-Fi 이름, 앱 이름, 시간대로 "집", "회사", "헬스장", "연인"을 단정하지 않는다. A/B로 부르고 사용자가 명명하게 둔다.
- **건강·정신 상태를 진단하기.** 수면이 짧다는 관측과 "수면 장애"는 다르다. 중독·우울·불안 같은 임상 용어를 쓰지 않는다.
- **인격이나 의지를 평가하기.** "의지가 약하다", "중독됐다", "산만하다"는 데이터에서 나오지 않는다. **행동을 서술하고 구조를 설명하되 사람을 평가하지 않는다.**
- **도덕적 어조.** 화면 시간이 길다는 것 자체는 나쁜 게 아니다. 사용자가 문제라고 여긴 것에 대해서만 개선을 논한다.
- **비교 규범 만들기.** "평균보다 많습니다" 같은 말은 근거 데이터가 없으면 쓰지 않는다.
- **민감한 내용 들여다보기.** 알림 본문, 메시지, 검색어, 사진 내용은 통계에 필요하지 않다. 발신 앱과 시각만으로 충분하다.

### 특히 조심할 표현

| 쓰지 말 것 | 대신 |
|---|---|
| "중독적으로 확인합니다" | "1회 평균 21초로 매우 짧게 자주 엽니다" |
| "수면이 부족합니다" | "폰을 놓은 시각부터 다시 켠 시각까지가 중앙값 5.8시간입니다" |
| "집중력이 낮습니다" | "30초 미만 세션이 54%입니다" |
| "회사에 있는 시간" | "Wi-Fi 밖에 있던 시간" |
| "쓸데없이 켭니다" | "앱을 열지 않고 끈 세션이 250번입니다" |

## 7. 전체 보고서 구조

순서에 이유가 있다.

```
1. 데이터 범위        — 무엇을 몇 일치 봤는지. 맨 앞에 둔다.
2. 요약 수치          — 중앙값·범위와 함께
3. 시간 축            — 하루 리듬, 날짜별 추이
4. 장소 축            — 있으면. 다른 축들의 원인 후보가 된다
5. 앱 축              — 사용량·성격·전환
6. 발견               — 교차 분석의 결과. 등급 순
7. 제안               — 우선순위 순
8. 한계와 정정 이력   — 맨 뒤. 무엇을 못 봤고 무엇을 고쳤는지
```

**8번을 빼지 않는다.** 한계를 밝힌 보고서가 밝히지 않은 보고서보다 항상 더 유용하다. 이전 분석을 수정했다면 무엇이 왜 바뀌었는지 표로 남긴다.
