# 확장 설계 기록

구현하지 않기로 한 것들의 설계를 남긴다. "왜 안 했는가"와 "하게 되면
어떻게"가 코드 밖으로 사라지지 않게 하는 문서다.

## 1. 맥락 조건의 에이전트화 — 조건 어휘를 앱이 소유하지 않는다

### 문제

루틴의 발화 조건은 현재 시간·요일 두 축이다(`ProposalRow.conditionHours/
Weekdays`, `PatternWatcher.inCondition`). 결정 로그에는 8축(시각·요일·앞 앱·
네트워크·BT·소리 모드·충전·배터리)이 쌓이고 심층 분석 에이전트는 그 축에서
갈림을 찾을 수 있는데, **출력 스키마·실험 도구·발화 검사에 그 칸이 없어서**
"이동 중일 때만" 같은 발견을 집행에 옮길 수 없다.

### 기각한 안 — 조건 축 하드코딩 확장 (3축 확장)

`conditionNetwork`·`conditionBt`·`conditionRinger` 컬럼을 추가하는 안.
동작은 하지만, 조건 어휘를 앱이 소유하게 된다 — 축이 하나 늘 때마다
스키마·검사·도구·지침서가 같이 늘어나고, 어휘는 영원히 개발자의 상상력
안에 갇힌다. 발견의 지능은 에이전트에 있는데 표현의 어휘는 앱에 있는
비대칭이 굳는다.

### 채택 방향 — 조건의 지능은 에이전트가, 앱은 평가만

**단기 (배치 캐시형).** 에이전트가 조건을 구조화 표현식으로 기술하고,
앱은 축의 의미를 모른 채 스냅샷 값과 대조 평가만 한다.

```json
"condition": { "all": [
  { "axis": "network", "eq": "cellular" },
  { "axis": "hour",    "in": "9-16" },
  { "axis": "ringer",  "ne": "silent" }
] }
```

- 앱 쪽 변화: `inCondition` 을 표현식 평가기로 교체(축 이름 → 그 순간의
  스냅샷 필드 조회, `eq/ne/in` 세 연산이면 충분). `ProposalRow` 에는
  표현식 JSON 컬럼 하나만.
- **착수 범위는 그 컬럼 하나로 끝나지 않는다.** 함께 바뀌는 곳:
  `Db.version` 승격 + `AutoMigration(10→11)` + `app/schemas/11.json` 커밋
  (기존 관례 그대로) · `deep-analysis.md` 의 조건 형식과 출력 스키마
  (`conditionHours`/`conditionWeekdays` → 표현식) · `start_experiment`
  도구 인자와 `DeepAnalyzer.valid()` · 그리고 조건을 화면에 설명하는 네
  지점(`PatternWatcher` 상단 KDoc 의 "함께 고쳐야 하는 곳" 목록 참고).
- 축 추가 = 스냅샷([DecisionContext.capture])에 필드 하나 추가일 뿐,
  스키마·도구·지침 확장이 필요 없다. 에이전트는 입력에서 본 축 이름을
  그대로 조건에 쓴다.
- 실험·만료·롤백은 지금 구조 그대로 표현식을 담으면 된다.
- 검증: 앱은 축 이름이 스냅샷에 실존하는지만 확인하고, 모르는 축이 오면
  그 항목을 무시(부분 평가)하되 로그를 남긴다.

**장기 (순간 판단형).** 온디바이스 LLM 이 충분해지면, 발화 직전
"지금 이 맥락에 어울리는가"를 소형 모델이 직접 판정한다. 배치 에이전트는
기준(메모리·검증된 규칙)을 만들고, 순간 모델이 그 기준을 적용한다.
표현식 캐시는 그때 폴백이 된다.

### 채택 기준

수락 루틴이 5개 안팎인 동안은 표현식 캐시로 충분하다. 순간 판단형은
호출 비용이 0에 수렴할 때(온디바이스)만 의미가 있다.

## 2. 개인 맥락 사전(메모리)의 외부 프로세스 연동

앱은 입구만 제공한다 — 구현 완료:

- **저장**: `files/memory.md`, 한 줄 항목 `- [MM/dd] 내용`. 없어도 모든
  기능이 그대로 돈다(무의존).
- **넣기**: 심층 분석 에이전트의 `remember(text)` 도구. "반복 확인된
  사실만"이 지침 규칙이다.
- **읽기**: 1차 분석·심층 분석 프롬프트에 '사용자 메모리'로 자동 포함.

외부 메모리 프로세스는 파일을 꺼내(`adb shell run-as com.routineai cat
files/memory.md`) 정리·요약·수명 관리를 하고, 같은 형식으로 되돌려 놓으면
된다. 앱은 그 결과를 다음 분석에서 그대로 소비한다. 상한(120줄)을 넘으면
앱은 오래된 줄부터 버린다 — 더 나은 정리는 외부의 몫이다.

발전 방향: 메모리에서 여러 번 재확인된 항목을 해석 지침서의 부록
(learned-rules)으로 승격 — "이 사용자의 판단 기준" 그 자체가 자라는 구조.

## 3. 보류 중 기능 — 코드에 복원 지점이 있다

| 기능 | 위치 | 상태 |
|---|---|---|
| 방해 예산 (24시간 후보 3개·카테고리 1개) | `PatternWatcher.canSurface` 주석 | 보류 — 기록은 계속 쌓임 |
| 맥락 버킷 거절 학습 (같은 버킷 2회 거절 시 침묵) | `PatternWatcher.rejectedHereBefore` 주석 처리된 한 줄 | 보류 — 기록은 계속 쌓임 |
| 자동 실행 (수락 루틴의 무언 실행) | `PatternWatcher` 헤더 주석 | 보류 — suggestAutoRun 판정은 계속 기록됨 |

셋 다 "억제·자동화는 최소로, 판단 재료는 전부 기록"이라는 데모 방침에
따른 보류다. 데모 후 사용량이 늘면 재검토한다.

## 4. 기타 확장 아이디어 (설계 전)

- **어긋남 트리거**: "평소보다 2시간 늦은 기상" 같은 기준선 편차를
  트리거로. 상시 기준선 계산이 필요해 배치 통계의 상시화가 선행 조건.
- **타이밍 밴딧**: 팝업 타이밍·선택지 순서 같은 연속 조정을 온디바이스
  밴딧이 맡고, LLM 은 구조(조건·서사)만 — 이층 학습.
- **루틴의 은퇴**: 무시율 상승을 패턴 소멸로 읽고 스스로 정리를 제안.
